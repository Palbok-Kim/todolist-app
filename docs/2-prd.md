## 1. 개요와 목표

TodoList는 인증된 사용자가 자기 할일을 시작일·종료일과 함께 관리하고 캘린더(월·주·일)에서 보는 웹 앱이다. 문제 정의(P1~P3)는 도메인 정의서 1장을 따른다.

**비즈니스 목표**
- G1 (확정): 동시 접속 사용자 1000명을 수용한다 (측정 기준은 NFR-01~03, NFR-16)
- G2 (확정): 1인 개발로 2일 안에 핵심 기능(P0)의 MVP를 구현하고 검증한다

**성공 지표 (출시 판정 기준)**

| ID | 지표 | 목표 | 측정 방법 | 구분 |
|----|------|------|-----------|------|
| KPI-01 | P0 기능의 수용 기준 통과율 | P0 FR에 연결된 AC 100% 통과 (4장 표에서 (P1)로 표시한 AC 제외) | AC별 수동 테스트 체크리스트 (Day 2 종료 시) | 가정 |

**판정 원칙 (확정)**: 측정 결과가 목표에 못 미치면 해당 KPI를 달성으로 표시하지 않고 측정값을 그대로 기록한다. 로컬 환경 부하 테스트 결과만으로 운영 환경의 동시 접속 1000명 지원이 검증됐다고 보지 않는다 (OI-12).

출시 후 사용 지표(가입 후 첫 할일 등록 전환율 등)는 분석 도구가 범위 외이므로 이번 PRD에서 정의하지 않는다.

## 2. 목표 사용자

- 학생, 20대~50대 직장인 (확정)
- 개인 일정·과제·업무 할일을 날짜 단위로 관리하려는 사용자. PC 웹에서 주로 쓰고 모바일 브라우저로도 확인한다 (사용 환경은 가정)
- 페르소나별 상세 시나리오는 작성하지 않는다 (확정)

## 3. 범위

**In Scope (MVP)**
- 도메인 정의서 FR-01 ~ FR-08 (우선순위는 4장)
- 웹 앱 + 반응형 UI (모바일은 반응형 웹으로만 대응)
- 비기능 요구사항 NFR-01 ~ NFR-16 (5장, NFR-14 접근성 제외)

**Out of Scope**
- 도메인 정의서 7장 범위 외 항목 전체 (공유·협업, 반복 일정, 알림, 하위 할일, 우선순위·태그, 소셜 로그인)
- 네이티브 모바일 앱, PWA·오프라인 지원 (확정: 웹 우선, 모바일은 반응형만)
- 접근성(WCAG, 스크린리더, 키보드 전용 조작 등) (확정)
- 페르소나별 상세 시나리오 (확정)
- 다국어(i18n): 한국어 UI만 제공 (가정)
- 비밀번호 찾기/재설정, 이메일 인증 (가정)
- 사용 분석·모니터링 대시보드 (가정)
- OI-08(캘린더에서 직접 등록·드래그), OI-09(회원 탈퇴): MVP 범위 외 (도메인 정의서 7장, OI-09는 R-10)

### 4.1 입력 검증 규칙 (OI-14)

도메인 정의서에 없는 회원가입 검증과 입력 길이 한도를 정한다. 위반 시 BR-15와 같이 저장하지 않고 사유를 알린다(ERR-01, `fields`에 필드별 사유). **프론트엔드와 백엔드 모두 같은 규칙으로 검증한다 (확정).** 문자열은 앞뒤 공백을 제거한 뒤 검증한다. 단, **비밀번호는 trim 등 어떤 자동 공백 제거도 하지 않고 입력값 그대로 검증·해시·비교한다 (확정)**. 회원가입·로그인·비밀번호 변경과 프론트엔드·백엔드 모두 같다.

| ID | 대상 | 규칙 | 구분 |
|----|------|------|------|
| VR-01 | User.email | 필수, 이메일 형식, 최대 254자. 소문자로 정규화해 저장하고 대소문자 무시로 중복 검사. 중복이면 ERR-04 | 가정 |
| VR-02 | 비밀번호 | 15~128자. 문자 종류(영문·숫자·특수문자) 조합은 강제하지 않는다 | 확정 |
| VR-03 | User.name | 필수, 1~50자 | 가정 |
| VR-04 | User.timezone | IANA 시간대 이름(예: `Asia/Seoul`)만 허용 (4.2) | 확정 |

**로그인 입력 검증 (확정, 위임 결정(2026-11-04), AQ-04)**: 로그인에는 VR-02의 15자 하한을 적용하지 않는다(15자 미만 비밀번호가 ERR-03과 다른 응답이 되면 안 된다). email과 비밀번호는 필수이고, email은 VR-01의 형식·최대 254자를 따르며, 비밀번호는 128자를 넘으면 ERR-01로 거부한다. 이 거부는 비밀번호 확인 전의 형식 검사라 계정 존재 여부를 드러내지 않는다. 그 밖의 비밀번호는 15자 미만이어도 검증 없이 비교하고 틀리면 ERR-03이다. 이 ERR-01 거부는 NFR-10의 실패 횟수에 넣지 않고, 형식 검사는 제한 확인(ERR-06)보다 먼저 한다.

### 4.2 시간대 정책 (확정, OI-10)

- 회원가입 시 브라우저의 `Intl.DateTimeFormat().resolvedOptions().timeZone` 값을 자동으로 감지해 함께 보낸다. 가입 화면에 입력란은 두지 않는다
- 회원가입 시 감지한 값이 없거나 VR-04를 통과하지 못하면 `Asia/Seoul`로 저장한다 (확정, 국내 사용자 우선). 이 대체는 회원가입 자동 감지에만 적용한다
- 사용자는 설정 화면(UC-03, FR-03의 P0 부분)에서 시간대를 바꿀 수 있어야 한다 (확정). 바꾸면 이후 '오늘'과 상태 판정이 새 시간대 기준이 된다 (AC-13). 설정 화면에서 VR-04를 통과하지 못한 값은 대체하지 않고 ERR-01로 거부한다 (확정, 위임 결정(2026-11-04))
- **시각** 데이터(createdAt, updatedAt, completedAt)는 UTC로 저장하고, 화면에서 사용자 시간대로 변환해 표시한다. 화면에 표시하는 시각 값은 할일 편집 화면의 '마지막 수정'(updatedAt) 한 줄이다 (확정, 위임 결정(2026-11-04)). 검증: 시간대를 바꾼 뒤 같은 할일의 '마지막 수정'이 새 시간대로 변환돼 표시된다 (SC-12)
- **날짜만 의미하는** 데이터(startDate, endDate)는 시간대 변환을 하지 않는다. 저장·전송·표시 모두 `YYYY-MM-DD` 문자열 그대로 다룬다 (6장 날짜 처리). 검증: 서버와 브라우저의 시간대를 `Asia/Seoul`이 아닌 값(예: UTC, `America/Los_Angeles`)으로 바꿔도 저장한 날짜가 그대로 조회·표시된다

### 4.4 비밀번호 변경 정책 (확정, 위임 결정(2026-11-04))

- 현재 비밀번호가 틀리면 ERR-01로 거부한다(`fields`의 필드는 `currentPassword`) (AC-21)
- 이 실패는 NFR-10의 로그인 실패 횟수에 넣지 않는다 (AC-21)
- 변경에 성공하면 그 사용자의 모든 리프레시 토큰을 폐기하고 현재 세션에는 새 액세스·리프레시·CSRF 토큰을 발급해 현재 기기의 로그인은 유지한다 (AC-20, BR-16, 사용자 결정(2026-11-04)의 후속, 위임 결정(2026-11-04)으로 확정). 다른 기기는 갱신이 거부되므로 이미 받은 액세스 토큰이 만료되는 최대 15분 뒤에 로그인을 요구한다. 이 15분은 R-08과 같은 잔여 위험이다

(2) **리프레시 토큰**: JWT가 아닌 불투명 무작위 값(`crypto.randomBytes` 32바이트 이상), 만료 7일이고 갱신할 때마다 새 토큰의 만료가 그 시점부터 7일이다(슬라이딩, OI-18). DB에는 SHA-256 해시만 저장하고 원문은 저장하지 않는다. `HttpOnly` 쿠키, `SameSite=Strict`, `Path`는 토큰 갱신·로그아웃 경로를 모두 포함하는 인증 API 공통 접두사 하나로 한정하며(구체 경로는 설계서, 그 접두사 아래의 다른 요청에도 쿠키가 전송되지만 쓰지 않는다, OI-19) `Secure` 조건은 액세스 토큰과 같다. (3) **회전과 재사용 감지**: 갱신할 때마다 새 리프레시 토큰을 발급하고 이전 것은 폐기한다. 회전으로 폐기된 토큰이 다시 오면 폐기 시각(`revoked_at`)으로부터 10초(유예 시간, `config.js` 설정값) 이내인 경우 재사용으로 보지 않고 계열은 폐기하지 않은 채 ERR-02로 거부만 한다(동시 갱신·응답 유실 뒤 재시도의 오판 방지). 10초를 넘겨 다시 오면 재사용(복제·탈취 의심)으로 보고 같은 로그인 계열(family)의 토큰을 모두 폐기한 뒤 ERR-02로 거부한다. 판단은 `revoked_at` 컬럼만 쓴다(스키마 변경 없음). 로그아웃·비밀번호 변경으로 계열이 이미 폐기된 토큰은 유예 안이든 밖이든 어차피 갱신이 거부되므로 회전 폐기와 구분할 필요가 없다. 같은 토큰으로 동시에 오는 갱신 요청은 DB 행 잠금(`FOR UPDATE`)으로 직렬화해 하나만 성공시키고, 나머지는 폐기 직후의 재제출이라 유예 안이므로 방금 성공한 새 토큰을 폐기하지 않고 ERR-02로 거부만 한다(OI-20). 프런트는 갱신이 실패하면 원 요청을 한 번만 재전송해 보고(쿠키는 브라우저 탭 간에 공유되어 다른 탭이 받은 새 쿠키가 이미 있을 수 있다), 그래도 ERR-02면 `onUnauthorized`로 로그인을 요구한다(11장). (4) **토큰 갱신 엔드포인트**: 액세스 토큰 없이 리프레시 쿠키만으로 호출하며 인증 미들웨어 앞의 공개 라우트 그룹에 둔다. 성공하면 새 액세스·리프레시·CSRF 토큰을 쿠키로 발급하고, 실패(없음·만료·폐기·재사용)는 ERR-02다. 로그인 실패 제한(NFR-10) 대상이 아니다. (5) 회원가입이 끝나면 로그인과 같이 액세스·리프레시·CSRF 쿠키를 발급해 자동으로 로그인한다 (확정, 위임 결정(2026-11-04). 리프레시 쿠키 추가는 사용자 결정(2026-11-04)). (6) 로그아웃은 BR-01대로 쿠키를 모두 지우고 리프레시 쿠키가 있으면 그 계열을 DB에서 폐기한다(폐기에 실패해도 쿠키는 지운다). 비밀번호 변경은 4.4를 따른다. **잔여 위험**: 액세스 토큰은 서버가 즉시 무효화하지 않으므로 로그아웃·비밀번호 변경 뒤에도 탈취된 액세스 토큰은 만료(최대 15분) 전까지 재사용될 수 있다. 리프레시 토큰은 서버에서 즉시 폐기된다(R-08). 유예 10초 안에 폐기된 토큰을 쓰는 탈취 재사용은 계열 폐기로 이어지지 않고 거부만 되므로 탈취자가 새 토큰을 얻지는 못하며 잔여 위험은 감지가 늦어지는 것뿐이다(R-14). 이 위험은 기술 문서(설계서)에도 명시한다. 액세스 토큰 검증은 DB를 조회하지 않고 서버 세션 저장소도 두지 않지만, 리프레시 토큰은 DB에 저장한다(R-12) | 검증: 만료·위조 토큰으로 요청 시 ERR-02(AC-02), `none`·HS256 등 HS384가 아닌 알고리즘 토큰 거부, 48바이트 미만 키로 기동 거부, 만료된 액세스 토큰과 유효한 리프레시 토큰으로 요청 시 자동 갱신 성공(AC-22), 만료·폐기된 리프레시 토큰 거부(AC-23), 폐기 후 10초 이내의 재사용은 ERR-02이고 계열은 유지(최신 토큰으로 갱신 성공), 10초를 넘긴 폐기 값 재사용 시 계열 전체 거부(AC-24), 같은 리프레시 토큰으로 동시 갱신 2건 중 1건만 성공하고 패자 뒤에도 승자의 새 토큰으로 갱신 성공, DB에 리프레시 토큰 원문이 없고 해시만 있음 | 확정 (JWT, HS384, 리프레시 토큰 기법: 사용자 결정(2026-11-04), OI-11의 이전 결정을 대체) / 확정 (위임 결정(2026-11-04): 만료 15분·7일, 쿠키 속성과 `Path` 접두사, 클레임, 회전·재사용 감지·계열 폐기 방식, 폐기 후 10초 유예, 키 길이, OI-18~21) |

| NFR-10 | 보안 (무차별 대입) | 로그인 **실패** 횟수를 IP별과 계정(email)별로 함께 세서 제한한다. 같은 IP에서 15분 안에 실패가 10회 쌓이면 그 IP의 다음 로그인 시도부터, 같은 계정에 15분 안에 실패가 5회 쌓이면 그 계정의 다음 로그인 시도부터 ERR-06(429)으로 거부한다(수치는 가정). 제한에 걸린 동안에는 비밀번호를 검증하지 않고 거부하므로 올바른 비밀번호여도 로그인되지 않는다(위임 결정(2026-11-04), AC-15). 제한은 시간 창이 지나면 풀리며 영구 잠금은 하지 않는다(R-09). 비밀번호 변경의 현재 비밀번호 불일치는 세지 않는다(4.4). 성공한 로그인은 세지 않으므로, 부하 테스트 셋업에서 한 IP로 사전 생성 계정 1000개가 로그인해도 제한에 걸리지 않는다(NFR-01). **테스트 IP 예외는 원칙적으로 두지 않는다.** 불가피하면 격리된 테스트 환경에서만 적용하고, 운영 환경에서는 켤 수 없어야 한다 | 수동 테스트: 같은 계정으로 5회 실패한 뒤 다음 시도는 올바른 비밀번호여도 429(AC-15), 같은 IP에서 여러 계정으로 10회 실패한 뒤 다음 시도는 429, 시간 창이 지나면 로그인 가능, 성공 로그인은 제한에 영향 없음(부하 테스트 셋업으로 확인). 운영 설정에서 IP 예외가 켜지지 않음을 확인 | 확정 (적용·컷 불가, 실패 기준, IP·계정 병행, 예외 금지, 제한 중 비밀번호 미검증) / 가정 (수치) |

CSRF 헤더 없이 로그아웃해도 성공 확인(AC-16). 토큰 갱신 성공 직후 응답으로 받은 새 CSRF 토큰으로 상태 변경 요청이 성공하고, 갱신 전 CSRF 토큰은 새 액세스 토큰과 연계되지 않아 403 | 확정 (적용, 방식, 로그아웃 제외, 토큰 갱신 제외와 CSRF 재발급: 위임 결정(2026-11-04), OI-19) / 가정 (로그인 전 요청 제외) |

| 부하 테스트 환경 | 이번 범위에서 부하 테스트를 하지 않는다(사용자 결정(2026-11-05)). 다시 도입하더라도 로컬 결과만으로 운영 환경 1000명 지원을 검증했다고 보지 않는다 (1장 판정 원칙) | 확정 (OI-12) |

## 11. 후속 설계 문서로 넘기는 항목

PRD에는 만족해야 할 요구사항과 검증 방법만 둔다. 아래 구현 세부는 설계서에서 정한다.

- scrypt 파라미터 값(N, r, p, maxmem), salt 길이, `passwordHash` 저장 포맷(알고리즘·파라미터·salt·해시), 파라미터 변경 시 재해시 방식, 해시 동시 처리를 위한 libuv 스레드 풀 크기 (NFR-06, NFR-16)
- 없는 email로 로그인할 때도 응답 시간으로 존재 여부가 드러나지 않게 하는 방법 (ERR-03)
- 로그인 실패 카운터의 저장 위치와 시간 창 방식. 제한 중 거부한 시도는 실패 횟수에 세지 않는다(위임 결정(2026-11-04): 세면 공격이 이어지는 동안 제한이 풀리지 않아 R-09가 악화된다), 프로세스 다중화(R-03) 시 공유 방법, 리버스 프록시 뒤에서 클라이언트 IP를 얻는 방법(운영은 배포 문서), 로컬 개발 프록시(Vite) 뒤에서 클라이언트 IP를 얻는 방법(SO-16으로 정함: 로컬에서 모든 요청이 프록시 IP로 보이면 IP별 제한이 전역 잠금이 된다), 만료 항목 정리와 보관 키 수 상한(PQ-10), 격리 테스트 환경용 IP 예외를 운영에서 켤 수 없게 하는 방법 (NFR-10)
- CSRF 토큰 구조(HMAC 입력값, JWT 식별자는 `jti`), 쿠키·헤더 이름, 서명 키 관리. 토큰 갱신 때 새 `jti`로 재발급한다 (NFR-15)
- 인증 토큰 세부 (NFR-07, 사용자 결정(2026-11-04)): 액세스·리프레시·CSRF 쿠키 이름, 쿠키 `Max-Age`(액세스·CSRF 15분, 리프레시 7일), 리프레시 쿠키 `Path`(Path 속성은 하나뿐이라 토큰 갱신·로그아웃 경로를 모두 포함하는 인증 API 공통 접두사 하나로 둔다. 그 접두사 아래의 다른 요청에도 쿠키가 전송되지만 쓰지 않는다. 이 사실을 설계서에 명시, OI-19), 리프레시 재사용 감지 유예 시간(10초)의 `config.js` 설정값 이름(NFR-07, OI-20), 토큰 갱신 경로, JWT 클레임 이름과 `jti` 생성 방식
- JWT 서명 키 관리 (NFR-07, R-13): 환경 변수 이름, 48바이트 이상 무작위 키 생성 방법, 기동 시 길이 검사(디코딩 후 바이트 수 기준), JWT 서명 키와 CSRF 서명 키를 분리할지, 키 교체 절차(교체하면 발급된 액세스 토큰이 모두 무효가 되고 리프레시로 복구되는지, 유출 시에는 리프레시 토큰도 모두 폐기)
- 리프레시 토큰 저장·갱신 (NFR-07, OI-18, OI-21): `refresh_tokens`([7-erd.md](./7-erd.md) ER-08) 쿼리, 해시로만 조회, 갱신 트랜잭션(행 잠금 → 폐기 → 새 행 INSERT), 재사용 감지 시 계열 폐기(폐기 후 유예 10초 이내는 `revoked_at`으로 판단해 거부만, OI-20), 로그아웃·비밀번호 변경 시 폐기 범위, 로그인 때 만료 행 정리와 `// LIMIT:` 주석
- 프런트의 갱신 처리 (DL-14): ERR-02를 받으면 갱신을 한 번만 시도하고 동시 요청은 하나의 갱신을 공유(single-flight)한 뒤 원 요청을 한 번 재시도한다. 갱신 요청 자체는 재시도하지 않고, 갱신이 실패하면 원 요청을 한 번만 재전송해 보고(쿠키는 탭 간에 공유되어 다른 탭이 받은 새 쿠키가 이미 있을 수 있다. 이 재전송이 ERR-02여도 다시 갱신하지 않는다), 그래도 ERR-02면 `onUnauthorized`로 만료 안내와 로그인 화면 이동을 한다. 여러 탭의 동시 갱신은 폐기 후 10초 유예(NFR-07, OI-20)로 처리한다
- 인증(ERR-02)과 CSRF(ERR-08) 검사 순서: 인증을 먼저 검사한다(위임 결정(2026-11-04). CSRF 토큰이 JWT 식별자에 연계되므로 유효한 JWT가 있어야 CSRF를 검증할 수 있다). 만료된 액세스 토큰의 상태 변경 요청은 ERR-02이고 클라이언트가 토큰 갱신 후 다시 보낸다(사용자 시나리오 SC-16). 갱신이 실패하면 원 요청을 한 번 재전송해 보고 그래도 ERR-02면 SC-03처럼 재로그인을 유도한다. 토큰 갱신은 인증·CSRF 검사 앞의 공개 라우트다 (NFR-07, NFR-15)
- 카테고리 이름 중복 검사(BR-14: trim 후 대소문자 무시)를 DB 제약으로 보장하는 방법: `(user_id, lower(name))` 표현식 고유 인덱스로 정했고 위반은 ERR-04다 (위임 결정(2026-11-04), 7-erd.md EQ-03)
- 카테고리 삭제 확인(BR-06)에 쓸 할일 개수: 카테고리 목록 조회 응답에 카테고리별 할일 수를 포함해 얻는다 (위임 결정(2026-11-04)). 이 개수는 조회 시점의 안내 값이며 실제 이동 건수와 다를 수 있다 (AQ-08)
- pg 라이브러리가 `DATE`를 JS `Date`로 바꾸지 않도록 type parser(OID 1082)를 문자열로 설정하는 것 (6장)
- 현재 사용자 조회 (위임 결정(2026-11-04), AQ-03): 프런트의 인증 여부 판정(`RequireAuth`)과 사용자 정보(name, email, timezone) 읽기용으로 '현재 사용자 조회' API를 둔다. 인증 실패는 ERR-02다. 회원가입·로그인 성공 응답도 같은 사용자 정보를 담고 `passwordHash`는 담지 않는다. 경로·응답 필드 이름은 설계서에서 정한다 (FR-01, FR-03, 4.2)
- 캘린더 기간 조회 계약 (위임 결정(2026-11-04), AQ-07): `YYYY-MM-DD` 시작일·종료일 두 값으로 조회하고, 시작일이 조회 종료일 이하이고 종료일이 조회 시작일 이상인 할일(BR-12)을 완료·기한 초과 포함해 돌려준다. 응답 항목에 서버가 계산한 `status`를 포함한다(PR-06). 월간 그리드의 앞뒤 달 날짜 칸을 포함한 범위를 조회한다. 형식 오류, 시작일이 종료일보다 늦은 경우, 기간이 42일(월간 그리드 6주)을 넘는 경우는 ERR-01이다. 파라미터 이름과 응답 필드 이름은 설계서에서 정한다 (FR-08, NFR-05, WF-05)
