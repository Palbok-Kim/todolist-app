## 2. 시나리오 본문

### SC-01 회원가입 후 첫 로그인 (P0)

**목표**: 가입하지 않은 사람이 계정을 만들고 처음 로그인한다.

**사전 조건**: 로그인하지 않은 상태. 가입하려는 email로 가입한 계정이 없다.

**기본 흐름**
1. 사용자가 회원가입 화면에서 email, name, 비밀번호를 입력한다. 시간대 입력란은 없다 (PRD 4.2).
2. 클라이언트가 VR-01·VR-02·VR-03으로 검증하고, 브라우저에서 감지한 시간대를 함께 보낸다 (PRD 4.2).
3. 시스템이 같은 규칙으로 다시 검증하고(PRD 4.1), 시간대가 VR-04를 통과하면 그대로 저장한다. 비밀번호는 NFR-06대로 해시해 저장한다.
4. 시스템이 그 사용자의 기본 카테고리를 만든다 (BR-03, AC-01).
5. 시스템이 가입과 함께 자동으로 로그인 처리해 인증 쿠키(액세스·리프레시)와 CSRF 쿠키를 발급한다 (NFR-07, NFR-15).
6. 시스템이 할일 목록 화면을 보여 준다 (가정). 목록은 비어 있다.

**대안·예외 흐름**
- 2a. 시간대 값이 없거나 VR-04를 통과하지 못함: 오류로 처리하지 않고 `Asia/Seoul`로 저장한다 (PRD 4.2).
- 2b. email 형식·name·비밀번호 길이 위반: 저장하지 않고 해당 필드 옆에 사유를 표시한다 (ERR-01, PRD 7장).
- 2c. 비밀번호 앞뒤에 공백이 있음: 제거하지 않고 입력값 그대로 검증·해시한다 (PRD 4.1). 이후 공백을 뺀 값으로는 로그인할 수 없다 (NFR-06 검증 방법).
- 3a. 대소문자만 다른 email이 이미 있음: 가입을 거부한다 (VR-01, ERR-04).

**결과**: User 1건(timezone 포함)과 기본 카테고리 1건이 생긴다. 사용자는 로그인 상태로 할일 목록 화면에 있다.

### SC-02 로그인 실패와 실패 횟수 제한 (P0)

**목표**: 잘못된 정보로는 로그인할 수 없고, 반복 실패는 일정 시간 막힌다.

**사전 조건**: 가입된 계정 `a@example.com`이 있다. 로그인하지 않은 상태.

**기본 흐름**
1. 사용자가 틀린 비밀번호로 로그인한다.
2. 시스템이 ERR-03으로 거부한다. 없는 email로 시도해도 같은 메시지를 보여 준다 (ERR-03, AC-14).
3. 시스템이 IP별·계정별 실패 횟수를 센다 (NFR-10).
4. 같은 계정의 실패가 시간 창 안에 한도(NFR-10)에 이르면, 그 계정의 다음 로그인 시도는 비밀번호가 맞아도 확인하지 않고 ERR-06으로 거부하며, 잠시 후 다시 시도하라고 안내한다 (NFR-10, AC-15).
5. 시간 창이 지나 제한이 풀리면 사용자가 올바른 비밀번호로 로그인하고, 시스템이 인증 쿠키(액세스·리프레시)와 CSRF 쿠키를 발급해 할일 목록 화면을 보여 준다 (SC-01의 5·6단계와 같음, AC-15).

**대안·예외 흐름**
- 1a. 입력 형식 위반(필수 값 누락, email 형식·254자 초과, 비밀번호 128자 초과): ERR-01로 해당 입력란 아래에 사유를 표시한다. 15자 미만 비밀번호는 위반이 아니며 틀리면 ERR-03이다. 이 거부는 실패 횟수에 넣지 않는다 (PRD 4.1 로그인 입력 검증, ERR-01, NFR-10).
- 4a. 같은 IP에서 여러 계정으로 실패가 한도(NFR-10)에 이름: 그 IP의 다음 로그인 시도를 ERR-06으로 거부한다 (NFR-10).
- 4b. 성공한 로그인은 실패 횟수에 넣지 않는다 (NFR-10).
- 4c. 영구 잠금은 하지 않는다 (NFR-10, R-09).

**결과**: 실패하는 동안 인증 쿠키는 발급되지 않는다. 제한은 시간이 지나면 자동으로 풀린다.

### SC-03 미인증 접근과 세션 만료 후 재로그인 (P0)

**목표**: 인증되지 않았거나 세션이 끝났으면(리프레시 토큰이 없거나 만료·폐기됨) 로그인을 다시 요구한다.

**사전 조건**: (A) 로그인하지 않은 상태, 또는 (B) 7일 넘게 앱을 쓰지 않아 리프레시 토큰이 만료됐거나 로그아웃·비밀번호 변경·재사용 감지로 폐기된 상태 (NFR-07, BR-16). 액세스 토큰만 만료되고 리프레시 토큰이 유효한 경우는 로그인을 요구하지 않으며 SC-16이다.

**기본 흐름**
1. 사용자가 할일 목록 화면 주소로 접근한다.
2. 시스템이 목록을 보여 주지 않고 ERR-02로 응답한다. 클라이언트는 토큰 갱신을 한 번 시도하지만 리프레시 토큰이 없거나 만료·폐기돼 갱신도 ERR-02로 실패하고, 원 요청을 한 번만 재전송해도 같은 이유로 ERR-02다 (BR-01, BR-16, AC-02, AC-23, SC-16 3a).
3. 클라이언트가 로그인 화면으로 보낸다. 갱신 실패(ERR-02)로 보낸 경우 로그인 화면에 '로그인이 만료되었습니다' 류의 안내를 표시한다 (확정, 위임 결정(2026-11-04)).
4. 사용자가 다시 로그인하면 할일 목록 화면으로 이동한다 (확정, 위임 결정(2026-11-04)).

**대안·예외 흐름**
- 1a. (B) 상태에서 편집 화면에서 저장을 누름: 시스템이 ERR-02로 거부하고 저장하지 않으며 갱신도 실패해 로그인 화면으로 보낸다. 입력하던 내용은 보존하지 않는다 (가정). 갱신 요청 자체는 다시 시도하지 않는다 (NFR-07).
- 1b. 위조된 액세스 토큰(HS384가 아닌 알고리즘·`none` 포함): ERR-02로 거부한다. 유효한 리프레시 쿠키가 함께 있으면 갱신으로 이어지며 그 뒤는 SC-16과 같다 (NFR-07).

**결과**: 인증 없이는 어떤 할일 데이터도 보이지 않는다. 재로그인 후 새 토큰으로 계속 사용한다.

### SC-04 로그아웃 (P0)

**사전 조건**: 로그인한 상태.

**기본 흐름**
1. 사용자가 로그아웃을 누른다.
2. 시스템이 인증 쿠키(액세스·리프레시)와 CSRF 쿠키를 삭제하고 성공으로 응답한다. 리프레시 쿠키가 있으면 그 로그인 계열을 서버에서 폐기한다 (BR-01, BR-16, NFR-07, NFR-15, AC-16).
3. 클라이언트가 로그인 화면으로 보낸다.
4. 사용자가 뒤로 가기 등으로 목록에 다시 접근하면 SC-03처럼 로그인을 요구한다 (AC-16).

**대안·예외 흐름**
- 1a. 토큰이 이미 만료됐거나 없는 상태에서 로그아웃: 로그아웃은 인증·CSRF 검증 없이 호출할 수 있으므로(BR-01, NFR-15) 시스템은 2단계와 같이 쿠키를 지우고 성공으로 응답한다. 리프레시 쿠키가 있으면 폐기도 하며, 폐기에 실패해도 쿠키는 지우고 성공으로 응답한다 (AC-16).

**결과**: 이 브라우저는 미인증 상태가 되고 로그아웃 전 리프레시 토큰 값으로는 갱신할 수 없다 (AC-16). 이미 발급된 액세스 토큰은 서버가 즉시 무효화하지 않아 만료(최대 15분)까지 유효하다 (NFR-07 잔여 위험, R-08).

### SC-05 할일 등록 (P0)

**목표**: 시작일·종료일이 있는 할일을 등록한다.

**사전 조건**: 로그인한 상태. 기본 카테고리가 있다 (SC-01).

**기본 흐름**
1. 사용자가 할일 등록 화면을 연다.
2. 제목, 설명(선택)을 입력하고 시작일자·종료일자를 날짜 선택기에서 고른다 (FR-04, PRD 4장 FR-04 비고). 예: start=11-03, end=11-05.
3. 카테고리는 고르지 않는다. 드롭다운은 기본값 '기본' 그대로다 (PRD 7장).
4. 사용자가 저장을 누른다. 클라이언트와 서버가 BR-07·BR-08·BR-09, VR-05·VR-06으로 검증한다 (PRD 4.1).
5. 시스템이 할일을 기본 카테고리에 저장한다 (BR-04, AC-05). completed는 false로 시작한다 (가정).
6. 시스템이 목록에 새 할일을 '진행 중' 상태로 보여 준다 (도메인 4장).

**대안·예외 흐름**
- 3a. 카테고리를 고름: 그 카테고리로 저장한다 (FR-02). 카테고리 등록 화면이 컷되면(PRD 8장 컷 라인 4) 기본 카테고리만 고를 수 있다.
- 4a. start=11-05, end=11-04: 저장하지 않고 사유를 알린다 (BR-07, BR-15, ERR-01, AC-06). start=end는 허용한다 (BR-07).
- 4b. 날짜 하나를 비움: 저장하지 않는다 (BR-08, OI-01, ERR-01).
- 4c. 제목이 비었거나 공백뿐이거나 길이 초과: 저장하지 않는다 (BR-09, VR-05, ERR-01).
- 4d. 다른 사용자의(또는 없는) 카테고리 ID로 저장 시도: SC-15를 따른다 (BR-02, ERR-05).

**결과**: 할일 1건이 정확히 1개 카테고리에 속해 저장된다 (BR-04). 저장한 날짜는 시간대와 상관없이 그대로 표시된다 (PRD 4.2).

### SC-06 할일 수정 (P0)

**사전 조건**: 로그인한 상태. 본인 할일(start=11-03, end=11-05)이 있다.

**기본 흐름**
1. 사용자가 목록이나 캘린더에서 할일을 눌러 편집 화면을 연다 (FR-07).
2. 제목, 설명, 날짜, 카테고리를 바꾼다. 예: 제목을 바꾸고 start를 11-04로 바꾼다.
3. 사용자가 저장을 누르고, 시스템이 SC-05의 4단계와 같은 규칙으로 검증한다.
4. 시스템이 저장하고 바뀐 날짜로 상태를 다시 판정해 보여 준다. 이 예에서는 '진행 중'에서 '시작 전'이 된다 (도메인 4장, AC-17).

**대안·예외 흐름**
- 3a. 검증 실패: SC-05의 4a~4d와 같다 (BR-02, BR-07, BR-08, BR-09, BR-15, ERR-01, ERR-05).
- 3b. API로 categoryId 없이 보낸 경우: 기본 카테고리로 저장한다 (서버 규칙 BR-04). 화면의 드롭다운에는 빈 선택지가 없어 이 경우에 도달하지 않는다 (PRD 7장).
- 1a. 이미 삭제됐거나 다른 사용자의 할일: ERR-05 (BR-02, SC-15).
- 1b. 편집을 취소함: 아무것도 바뀌지 않는다 (가정).

**결과**: 할일이 바뀐 값으로 저장되고 updatedAt이 갱신된다.

### SC-07 할일 완료 표시·해제 (P0)

**사전 조건**: 로그인한 상태. 본인 할일(start=10-30, end=11-02, completed=false, 현재 '기한 초과')이 있다.

**기본 흐름**
1. 사용자가 편집 화면을 연다. 완료 표시는 편집 화면에서만 한다 (OI-07).
2. 완료로 표시하고 저장한다.
3. 시스템이 completedAt에 그 시각을 기록한다 (BR-13). 상태는 날짜와 상관없이 '완료'가 된다 (도메인 4장).
4. 사용자가 다시 편집 화면을 열어 완료를 해제하고 저장한다.
5. 시스템이 completedAt을 null로 되돌리고 날짜로 상태를 다시 판정한다. 이 예에서는 '기한 초과'로 돌아간다 (BR-13, AC-10).

**대안·예외 흐름**
- 2a. 완료 표시와 함께 다른 필드도 바꿈: SC-06의 검증을 함께 적용한다 (BR-15).

**결과**: completed·completedAt만 바뀌고 startDate·endDate는 그대로다.

### SC-08 할일 삭제 (P0)

**사전 조건**: 로그인한 상태. 본인 할일 1개가 있다.

**기본 흐름**
1. 사용자가 편집 화면에서 할일의 삭제를 누른다 (FR-06, BR-10).
2. 시스템이 삭제 확인을 요청한다 (BR-10).
3. 사용자가 확인하면 시스템이 할일을 물리 삭제하고 목록·캘린더에서 뺀다 (BR-10).

**대안·예외 흐름**
- 2a. 사용자가 확인을 취소: 삭제하지 않고 할일이 그대로 남는다 (BR-10, AC-11).
- 3a. 이미 없거나 다른 사용자의 할일: ERR-05 (BR-02).

**결과**: 할일이 복구할 수 없게 삭제된다(확인한 경우).

### SC-09 할일 목록 필터와 상태 판정 경계 (P0)

**목표**: 카테고리와 상태로 목록을 좁혀 본다.

**사전 조건**: 로그인한 상태. '업무' 카테고리와 기본 카테고리가 있고, 본인 할일이 아래와 같다 (모두 completed=false).

| 할일 | 카테고리 | startDate | endDate | 오늘(11-03) 상태 | 다음 날(11-04) 상태 |
|------|----------|-----------|---------|------------------|---------------------|
| T1 | 업무 | 11-03 | 11-03 | 진행 중 (종료일 당일) | 기한 초과 |
| T2 | 기본 | 11-01 | 11-03 | 진행 중 | 기한 초과 |
| T3 | 업무 | 11-04 | 11-06 | 시작 전 | 진행 중 |
| T4 | 업무 | 10-30 | 11-02 | 기한 초과 | 기한 초과 |

판정은 도메인 4장 규칙을 따른다 (AC-07, AC-08).

**기본 흐름**
1. 사용자가 할일 목록 화면을 연다. 필터가 없으면 본인 할일 전체가 기본 정렬(BR-11)로 나온다: T4, T2, T1, T3.
2. 상태 필터 '진행 중'을 고른다. 시스템이 서버에서 상태를 계산해(PRD 6장) T2, T1을 보여 준다 (AC-08).
3. 카테고리 필터 '업무'를 함께 고른다. 두 조건을 AND로 적용해 T1만 보여 준다 (BR-11).
4. 상태 필터를 '기한 초과'로 바꾼다. T4가 나오고, T4는 '진행 중' 필터에는 나오지 않는다 (AC-07).
5. 필터를 모두 해제하면 전체 목록으로 돌아간다 (BR-11).

**대안·예외 흐름**
- 2a. 다음 날(11-04)에 같은 필터를 고름: T1, T2는 '기한 초과'로, T3는 '진행 중'으로 나온다 (도메인 4장). 저장값은 바뀌지 않는다.
- 3a. 조건에 맞는 할일이 없음: 빈 목록과 안내 문구를 보여 준다 (가정).
- 1a. 다른 사용자의 할일은 어떤 필터에서도 나오지 않는다 (BR-02, AC-09).
- 3b. 다른 사용자의(또는 없는) 카테고리로 필터: ERR-05 (BR-02, SC-15).

**결과**: 필터는 조회 조건일 뿐 데이터를 바꾸지 않는다. 결과는 페이지네이션 없이 전체를 반환한다 (OI-15).

### SC-10 월간 캘린더 조회 (P0)

**사전 조건**: 로그인한 상태. 본인 할일 A(start=11-03, end=11-05), B(start=10-30, end=11-02, completed=false), C(start=11-10, end=11-10, completed=true)가 있다.

**기본 흐름**
1. 사용자가 캘린더 화면을 연다. 처음에는 오늘이 속한 달(2026년 11월)의 월간 뷰를 보여 준다 (가정).
2. 시스템이 그 달 기간에 걸친 본인 할일만 조회한다 (BR-02, NFR-05).
3. A는 3일, 4일, 5일 칸에 모두 표시된다 (BR-12, AC-12).
4. 달을 넘는 B는 11월 1일, 2일 칸에 표시되고, 10월로 이동하면 30일, 31일 칸에 표시된다 (BR-12).
5. 완료한 C와 기한 초과인 B도 표시하며, 상태는 색과 텍스트 라벨로 구분한다 (BR-12, PRD 7장).
6. 사용자가 할일을 누르면 편집 화면으로 간다 (SC-06) (가정).

**대안·예외 흐름**
- 1a. 화면 너비가 768px 미만(최소 360px): 칸에 제목 대신 할일 개수(점·숫자)를 보여 주고, 날짜를 누르면 그날 할일 목록을 보여 준다. 가로 스크롤은 없다 (NFR-12).
- 6a. 캘린더 칸에서 바로 등록하거나 드래그로 옮기기: 제공하지 않는다 (OI-08, MVP 범위 외).

**결과**: 데이터는 바뀌지 않는다.

### SC-11 주간·일간 캘린더 조회 (P1)

**사전 조건**: SC-10과 같다. PRD 8장 컷 라인 2에 따라 빠질 수 있다.

**기본 흐름**
1. 사용자가 캘린더 화면에서 '주'를 고른다.
2. 시스템이 오늘이 속한 주를 월요일 시작으로 보여 준다: 11-02(월) ~ 11-08(일) (OI-06). A는 3·4·5일, B는 2일에 표시된다 (BR-12, AC-18).

4. 이전/다음으로 주·일을 이동한다 (가정).

**대안·예외 흐름**

**결과**: 데이터는 바뀌지 않는다.

### SC-12 설정 화면에서 시간대 변경 (P0)

**목표**: 사용자가 자기 시간대를 바꾸면 '오늘'과 상태 판정이 새 시간대를 따른다.

**사전 조건** (AC-13과 같음): timezone=`Asia/Seoul`, 할일 start=end=11-03, completed=false. 현재 시각 2026-11-03 20:00 UTC (서울은 11-04 05:00). 이 할일은 현재 '기한 초과'다.

**기본 흐름**
1. 사용자가 설정(내 정보) 화면을 연다. MVP에서는 시간대 변경만 있는 최소 화면이다 (PRD 7장).
2. 현재 시간대 `Asia/Seoul`이 표시된다. 사용자가 `UTC`를 골라 저장한다. 시간대는 목록에서 고른다 (가정).
3. 시스템이 VR-04로 검증하고 저장한다.
4. 이후 '오늘'은 11-03(UTC)이 되고, 그 할일은 '진행 중'으로 다시 판정된다 (AC-13, PRD 4.2).
5. 할일의 startDate·endDate는 바뀌지 않는다 (AC-13). 할일 편집 화면의 '마지막 수정'(updatedAt)은 새 시간대로 변환해 표시한다 (PRD 4.2).

**대안·예외 흐름**
- 3a. IANA 이름이 아닌 값: 저장하지 않고 사유를 알린다 (VR-04, ERR-01). 가입 때와 달리 `Asia/Seoul`로 대체하지 않는다 (PRD 4.2).

**결과**: User.timezone이 바뀌고, 목록 필터(SC-09)와 캘린더 상태 표시(SC-10)가 새 기준을 따른다.

### SC-13 카테고리 관리 (P1)

**사전 조건**: 로그인한 상태. 기본 카테고리가 있다. PRD 8장 컷 라인 3·4에 따라 수정·삭제 또는 등록 화면이 빠질 수 있다.

**기본 흐름 (등록)**
1. 사용자가 카테고리 관리 화면에서 '업무'를 입력해 등록한다.
2. 시스템이 BR-14, VR-07로 검증하고 저장한다. 할일 등록·필터에서 '업무'를 고를 수 있게 된다.

**기본 흐름 (삭제)**
1. '업무'에 할일 2개가 있다. 사용자가 '업무'를 삭제한다.
2. 시스템이 옮겨질 할일 개수(2개)를 보여 주며 삭제 확인을 요청한다 (BR-06).
3. 확인하면 '업무'가 삭제되고 할일 2개는 기본 카테고리로 옮겨진다 (BR-06, OI-04, AC-04).

**대안·예외 흐름**
- 등록 2a. 같은 사용자에게 이미 있는 이름(앞뒤 공백 제거·대소문자 무시로 비교. 예: '업무', ' 업무 ', '기본'): 거부한다 (BR-14, ERR-04).
- 등록 2b. 이름이 비었거나 공백뿐이거나 30자 초과: 거부한다 (BR-14, VR-07, ERR-01).
- 수정 a. 다른 카테고리 이름을 바꿈: 등록과 같은 검증을 한다 (BR-14, BR-15).
- 삭제·수정 b. 기본 카테고리를 삭제하거나 이름을 바꾸려 함: 거부하고 사유를 알린다 (BR-05, ERR-01, AC-03). 화면에서는 기본 카테고리의 삭제·수정 버튼을 감춘다 (가정). 서버 검증은 그대로 둔다.
- 삭제 2a. 확인을 취소: 아무것도 바뀌지 않는다 (BR-06).

**결과**: 카테고리를 지워도 할일은 남는다. 사용자에게는 항상 기본 카테고리가 1개 있다 (도메인 3장).

### SC-14 내 정보 수정: name, 비밀번호 (P1)

**사전 조건**: 로그인한 상태. PRD 8장 컷 라인 1에 따라 가장 먼저 빠질 수 있다. 수정 범위는 OI-03, 관련 AC는 AC-19~AC-21이다.

**기본 흐름 (name)**
1. 사용자가 설정 화면에서 name을 바꿔 저장한다.
2. 시스템이 VR-03으로 검증하고 저장한다. email은 바꿀 수 없다 (OI-03, AC-19).

**기본 흐름 (비밀번호)**
1. 사용자가 현재 비밀번호와 새 비밀번호를 입력한다 (OI-03).
2. 시스템이 현재 비밀번호를 확인하고, 새 비밀번호를 VR-02로 검증한다. 두 값 모두 공백을 제거하지 않는다 (PRD 4.1).
3. 시스템이 새 비밀번호를 NFR-06대로 해시해 저장한다.
4. 이후 로그인에는 새 비밀번호만 통한다. 현재 기기의 로그인은 유지되고(새 토큰 발급), 다른 기기는 리프레시 토큰이 폐기돼 액세스 토큰이 만료된 뒤(최대 15분) 로그인을 요구한다 (PRD 4.4, R-08, BR-16, AC-20).

**대안·예외 흐름**
- name 2a. 비었거나 50자 초과: 거부한다 (VR-03, ERR-01).
- 비밀번호 2a. 현재 비밀번호가 틀림: 저장하지 않고 현재 비밀번호 필드에 사유를 알린다 (ERR-01). 이 실패는 로그인 실패 횟수(NFR-10)에 넣지 않는다 (PRD 4.4, AC-21).
- 비밀번호 2b. 새 비밀번호가 15자 미만 또는 128자 초과: 거부한다 (VR-02, ERR-01).
- 비밀번호 2c. 새 비밀번호 앞뒤에 공백이 있음: 그대로 저장하며, 이후 공백까지 똑같이 입력해야 로그인된다 (PRD 4.1).

**결과**: User.name 또는 passwordHash가 바뀐다. 회원 탈퇴는 제공하지 않는다 (OI-09, MVP 범위 외).

### SC-15 다른 사용자 데이터 접근 시도 (P0)

**목표**: 다른 사용자의 데이터는 존재 여부조차 드러나지 않는다 (KPI-04).

**사전 조건**: 사용자 U1, U2가 있다. U2의 할일 ID와 카테고리 ID를 U1이 알고 있다. U1이 로그인한 상태.

**기본 흐름**
1. U1이 U2 할일 ID로 조회·수정·삭제를 요청한다 (주소 직접 입력 등).
2. 시스템이 '없음'으로 응답한다 (BR-02, ERR-05). 없는 ID일 때와 같은 응답이다.
3. U1의 목록(SC-09)과 캘린더(SC-10)에는 U2 할일이 나오지 않는다 (BR-02, AC-09).

**대안·예외 흐름**
- 1a. U2 카테고리 ID로 할일 등록·수정이나 목록 필터, 또는 카테고리 수정·삭제: ERR-05 (BR-02).
- 1b. CSRF 토큰 없이 또는 다른 로그인의 CSRF 토큰으로 상태 변경 요청: ERR-08 (NFR-15).

**결과**: U2의 데이터는 바뀌지 않고, U1에게 노출되지 않는다.

### SC-16 액세스 토큰 만료와 자동 갱신 (P0)

**목표**: 오래 머문 뒤 저장해도 로그인이 끊기지 않고, 복제·탈취된 리프레시 토큰은 쓸 수 없다 (사용자 결정(2026-11-04)).

**사전 조건**: 로그인한 지 15분이 넘어 액세스 토큰은 만료됐고 리프레시 토큰은 유효하다(7일 안). 사용자가 할일 편집 화면에서 제목을 고쳐 둔 상태.

**기본 흐름**
1. 사용자가 저장을 누른다.
2. 시스템이 만료된 액세스 토큰으로 온 요청을 ERR-02로 거부한다. 이때는 저장하지 않는다 (NFR-07).
3. 클라이언트가 토큰 갱신을 한 번 요청한다. 같은 시점에 ERR-02를 받은 다른 요청이 있으면 하나의 갱신 요청을 공유한다 (DL-14, PRD 11장).
4. 시스템이 리프레시 토큰을 확인해 새 액세스·리프레시·CSRF 토큰을 발급하고 이전 리프레시 토큰은 폐기한다 (BR-16, NFR-07, NFR-15).
5. 클라이언트가 새 CSRF 토큰으로 원래의 저장 요청을 한 번 다시 보내고 저장된다. 사용자는 끊김을 보지 못한다 (AC-22).

**대안·예외 흐름**
- 3a. 갱신이 ERR-02로 실패: 클라이언트가 원 요청을 한 번만 재전송해 본다. 쿠키는 브라우저 탭 간에 공유되므로 다른 탭이 이미 갱신해 받은 새 쿠키가 있으면 재전송이 성공하고 사용자는 끊김을 보지 못한다 (AC-22, PRD NFR-07). 재전송도 ERR-02면(리프레시 토큰 만료·폐기) SC-03의 3·4처럼 로그인 화면으로 보내고 만료 안내를 표시한다. 입력 내용은 보존하지 않는다 (AC-23).
- 4a. 마지막 로그인·갱신 뒤 7일 넘게 사용하지 않음: 3a와 같다. 7일 안에 갱신하면 그 시점부터 다시 7일이다 (AC-23, PRD OI-18).
- 4b. 이미 갱신에 쓰여 폐기된 리프레시 토큰이 다시 제출됨: 폐기 후 10초 이내(여러 탭·동시 요청·응답 유실 뒤 재시도)이면 재사용으로 보지 않고 계열은 유지한 채 ERR-02로 거부만 하며, 3a의 재전송으로 새 쿠키가 쓰여 보통 성공한다 (AC-24, PRD OI-20). 10초를 넘겨 제출되면(복제·탈취 의심) ERR-02로 거부하고 그 로그인 계열의 리프레시 토큰을 모두 폐기한다. 최신 토큰을 가진 기기도 다음 갱신 때 로그인을 요구한다 (AC-24, BR-16)
- 4c. 다른 기기에서 비밀번호를 바꿈: 이 기기의 리프레시 토큰은 이미 폐기돼 있어, 액세스 토큰이 만료된 뒤 갱신이 실패하고 로그인을 요구한다 (PRD 4.4, AC-20, AC-23).

**결과**: 리프레시 토큰은 쓸 때마다 새것으로 바뀌고 같은 계열의 이전 토큰으로는 다시 갱신할 수 없다.
